# ADR-0006: Token-only authentication for the client portal

- **Status:** Accepted
- **Date:** 2024-09-15 (back-dated)
- **Deciders:** Sean Mousseau

## Context

Clients need to view, reply to, close, and reopen their tickets without a WordPress account. Forcing every client to create a WP login would dramatically reduce adoption — most helpdesk users are "I have a problem; I want to report it; I don't want another password to manage."

Three approaches were viable:

1. **Token-only.** Each ticket gets a random secret; the secret is included in portal URLs emailed to the client.
2. **WP user accounts.** Auto-create WP users on first submission; require login.
3. **Email magic links.** No persistent token — every portal visit triggers an email with a fresh URL.

## Decision

**The client portal authenticates by token alone. No WordPress account is required.**

- 20-character alphanumeric token generated by `wp_generate_password(20, false)`, stored in `_ticket_token` meta.
- Token expiry stored in `_ticket_token_exp` meta (default 90 days TTL).
- Token rotates on every successful lookup-form submission.
- Comparison uses `hash_equals()` after an explicit empty-token guard (so `hash_equals('', '')` cannot bypass).
- Expired tokens trigger the lookup form, which can resend a fresh link to the email on record.

## Consequences

### Costs

- **Tokens in URLs end up in logs.** Webserver logs, browser history, proxy caches, referer headers (mitigated by referer-policy meta on the portal). We accept this and document the 90-day TTL + rotation-on-lookup as compensating controls.
- **No persistent identity across tickets.** A client opens ticket A, then later opens ticket B from the same email — they're separate tokenized URLs. The My Tickets dashboard helps consolidate this **only for logged-in WP users**; anonymous clients get separate emails.
- **Compromised email = compromised tickets.** If the client's email account is breached, the attacker can read every portal-link email and access every ticket. This is true of magic links too, and arguably of any email-based system — including most password-reset flows. We document this in `security-model.md`.

### Benefits

- **Lowest friction onboarding.** "Click the link in your email" is the universally understood pattern.
- **No password management for the operator** — no password-reset support tickets, no breached-password handling, no MFA infrastructure.
- **No new attack surface** for credential stuffing or brute-force login attempts.
- **Naturally per-ticket scoping.** A leaked token only exposes one ticket, not the client's entire history.
- **Rotation is cheap** — a single meta update.

## Layered defences

Token-only auth carries risk; we mitigate with several layers:

1. **Constant-time compare** (`hash_equals()` + explicit empty-token guard).
2. **TTL expiry** — 90 days; configurable.
3. **Rotation on lookup** — even if a URL leaks via referer, a subsequent legitimate lookup invalidates it.
4. **Per-action rate limiting** with per-ticket scoping (`portal_close_<id>`, `portal_reopen_<id>`, `portal_reply_<id>` keys).
5. **Anti-spam** on every form action including portal reply/close/reopen.
6. **Nonce check** on every form POST in addition to the token.
7. **Capability check** for staff access (`edit_post` on the parent ticket).

## Alternatives considered

- **Auto-create WP users.** Rejected. Creates a meaningful operational burden (password resets, account merge when same person opens tickets from multiple addresses), and forces every helpdesk client to navigate the WP login UI — terrible UX for the "I just need help" persona.
- **Magic links per visit (no persistent token).** Considered seriously. Stronger security (no long-lived secret on disk) but worse UX (an email round-trip per visit) and worse cache behaviour (every visit invalidates the URL — bookmarks always break). The 90-day rotating token is a deliberate trade-off in favor of UX.
- **OAuth / SSO to a customer's existing identity provider.** Out of scope for a self-hosted plugin targeting small-to-medium WordPress sites. Possible future direction for enterprise-tier deployments.

## Implementation invariants

These are restated in `contract-portal.md` and `design-document.md`:

- Token comparison: `hash_equals()` after empty-token guard.
- Tokens rotate on every successful lookup-form submission.
- TTL is operator-configurable (default 90 days).
- All portal form actions require nonce + token + rate-limit + anti-spam — any failure rejects.
