# Glossary

Authoritative definitions of every term used across Simple WP Helpdesk docs and code. When a doc or PR uses one of these terms, this is what it means — no synonyms, no ambiguity.

If a term you need isn't here, add it. Better to over-define than to let definitions drift.

---

## Core nouns

### Ticket

A single support request. Stored as a `wp_posts` row with `post_type = helpdesk_ticket`. Has one client (`_ticket_email`), one status (`_ticket_status`), zero-or-one assignee (`_ticket_assigned_to`), zero-or-many replies (comments), zero-or-many internal notes (also comments), zero-or-many attachments.

### Reply (public reply)

A `wp_comments` row with `comment_type = helpdesk_reply` and (implicitly or explicitly) no `_is_internal_note` flag. Visible to the client in the portal. Visible to staff in the editor.

Sources of replies:
- Client via portal form.
- Client via inbound email webhook.
- Staff via ticket editor.
- System (auto-close notes, retention notes, merge breadcrumbs).

### Internal note

A `wp_comments` row with `comment_type = helpdesk_reply` **and** `_is_internal_note = 1`. Visible only to staff. **Must** be filtered from the portal view at the renderer level (not just the query level — defence in depth).

### Status

One of the configured workflow states for a ticket. Default labels: `Open`, `In Progress`, `Resolved`, `Closed`. Operator-customizable in **Settings → General → Custom Statuses**.

Three logical statuses have dedicated settings that track which operator-configured label means what:
- `swh_resolved_status` — triggers auto-close, shows close block in portal.
- `swh_closed_status` — disables replies, shows reopen block.
- `swh_reopen_status` — set when a closed ticket is reopened.

### Priority

One of the configured priority levels. Default: `Low`, `Medium`, `High`. Operator-customizable in **Settings → General → Custom Priorities**.

### UID (ticket UID)

The human-readable `TKT-<number>` identifier on a ticket. Stored in `_ticket_uid` meta. Used in:
- Email subjects (`[TKT-1234]`) — required for inbound webhook threading.
- Portal URLs are NOT keyed by UID (they use the post ID + token).

The numeric portion of the UID is monotonically increasing per site. It is NOT the same as the WordPress post ID.

### Token (portal token)

A 20-character alphanumeric string generated by `wp_generate_password(20, false)`. Stored in `_ticket_token` meta. Used as the authentication factor for anonymous portal access. Compared with `hash_equals()`. Rotates on every successful lookup-form submission. Has a configurable TTL (default 90 days) stored in `_ticket_token_exp`.

**Not** the same as the inbound-webhook bearer secret — that's a separate option (`swh_inbound_secret`).

### Portal

The token-authenticated frontend view of a single ticket. Rendered by `[submit_ticket]` or `[helpdesk_portal]` when a valid `swh_ticket` + `token` pair is in the URL. The "Helpdesk Page" setting controls which WordPress page hosts this.

### My Tickets dashboard

The card-list view rendered by either shortcode when the visitor is logged in as a WP user AND no specific ticket is in the URL. Lists all tickets where `_ticket_email` matches the logged-in user's email.

### Lookup form

The "Resend my ticket links" form. Visible to anonymous visitors who hit a portal URL without (or with an invalid / expired) token. Submitting an email address triggers a fresh portal-link email if the address matches any ticket. **Anti-enumeration:** the same success message is shown whether the email matched or not — we never confirm whether a given address has tickets.

## People

### Client

The person who submitted the ticket. Identified by `_ticket_email`. Has no WordPress user account necessarily. Authenticates to the portal via token.

### Technician

A WordPress user with the `technician` role (capability: `edit_posts`-equivalent on `helpdesk_ticket`). Can view, reply to, and modify tickets. With `swh_restrict_technicians` enabled, sees only their own assigned tickets.

### Administrator

A WordPress user with `manage_options`. Sees all tickets always. Configures plugin settings. Operates the danger-zone actions (purge, factory reset).

### Assignee

The technician currently assigned to a ticket (via `_ticket_assigned_to`). Receives admin notifications routed through `swh_get_admin_email()`.

### Default assignee

The technician set in **Settings → Assignment & Routing → Default Assignee** (`swh_default_assignee_id`). Auto-applied to every new ticket. Receives admin notifications when no specific assignee is set on a ticket.

### Watcher

A WordPress user added to a ticket via `_ticket_watchers` meta. Receives Cc on outbound staff replies. Distinct from the assignee.

### Fallback alert email

The address in **Settings → Assignment & Routing → Fallback Alert Email** (`swh_fallback_email`). Receives admin notifications when neither the assigned technician nor the default assignee resolves. Receives SLA breach digests. Not necessarily a WordPress user.

## Workflows

### Submission

The act of creating a new ticket via the frontend form. Goes through anti-spam, nonce, rate-limit gates, then `swh_create_ticket()`.

### Close

The act of transitioning a ticket from `Resolved` (or any non-closed status) to `swh_closed_status`. Initiated by:
- The client via the portal close form.
- A technician via the ticket editor.
- The auto-close cron job.

Fires `swh_ticket_status_changed` + `swh_ticket_closed`.

### Reopen

The act of transitioning a ticket from `swh_closed_status` back to `swh_reopen_status`. Initiated by:
- The client via the portal reopen form.
- A technician via the ticket editor.
- The inbound email webhook (auto-reopen on email reply).

Fires `swh_ticket_status_changed` + `swh_ticket_reopened`.

### Auto-close

The cron-driven transition of `Resolved` tickets to `Closed` after `swh_autoclose_days` days of inactivity. See `contract-cron.md`.

### Merge

The admin action of moving all replies from a source ticket onto a target ticket, then closing the source. Implemented in `class-ticket-editor.php`. Adds a system comment to both tickets as a breadcrumb.

### CSAT

Customer Satisfaction rating. A 1–5 star prompt rendered to the client immediately after they close a ticket (if `swh_csat_enabled` is on). Stored in `_ticket_csat` meta. Fires `swh_csat_submitted`.

## Process

### Plan

A document describing what a release will deliver, per-step / per-PR, with implementation detail, doc updates required, and test updates required. Written using the `superpowers:writing-plans` skill. See `planning-and-release-process.md`.

### Milestone

A GitHub milestone representing a release cycle. Has a theme. Contains a coherent set of issues.

### Release cycle

The full process from milestone kickoff to release tag. Three internal gates: feature → release, release → dev, dev → main.

### RC (release candidate)

A `release/vX.Y.Z` branch state that has had every planned feature/step merged in and is ready for the extended test suite (`extended-test-plan.md`).

### Gate

A merge or release gate, as defined in `planning-and-release-process.md`. Non-negotiable.

### Bundle

The shipping artifact: a `simple-wp-helpdesk.zip` built from the `simple-wp-helpdesk/` directory and uploaded to the GitHub Release on tag push.

## Settings / configuration

### Setting

An option-key entry stored in `wp_options`. All settings the plugin owns are prefixed `swh_` and live in `swh_get_defaults()`.

### Tab

A section of the **Tickets → Settings** admin page. Ten tabs in v4.0.x. See `contract-settings.md`.

### Group

The taxonomy used by `swh_get_option( $group, $key, $default )`. Not 1:1 with tabs — historical reasons. See `config-reference.md`.

### Defaults

`swh_get_defaults()` — the single source of truth for every option the plugin owns. Used by the installer, factory reset, and uninstall routines.

## Storage

### Meta

A post-meta (`wp_postmeta`) or comment-meta (`wp_commentmeta`) key. SWH meta keys are prefixed `_ticket_*`, `_is_*`, `_swh_*`, etc. Full catalog: `data-dictionary.md`.

### Transient

A WP transient (`wp_options` row with a TTL). SWH transients are prefixed `swh_*`. Used for short-lived state like the unread-count cache and report aggregates.

### Option

A `wp_options` row. Used for settings, persistent rate-limit state, and a few flags.

### CPT

Custom post type. SWH registers one: `helpdesk_ticket`. Stored in `wp_posts` with `post_type = helpdesk_ticket`.

### Visual regression suite

The manual Playwright-driven screenshot suite in `visual-regression-suite.md`. Required before `dev → main`.

## Things that look like terms but aren't

- **"Helpdesk"** — used colloquially to mean the plugin. Not a code identifier.
- **"Inbox"** — the admin ticket list view. Same thing as "ticket list"; both terms are used in docs.
- **"Drawer"** — the slide-out panel in the admin ticket editor.
- **"Conversation"** — the body of replies + internal notes on a ticket. Not a distinct storage primitive.
