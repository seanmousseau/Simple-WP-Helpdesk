# JS Architecture (v4.0+)

How JavaScript is authored, built, and shipped in Simple WP Helpdesk.

**Status:** decision locked v3.7.0 (issue #390), expanded across v4.0.x. As of v4.0.6 the build covers six entrypoints and is the canonical path for new JS.

---

## Decision

JS modules are authored in `simple-wp-helpdesk/assets/src/` and built via [`@wordpress/scripts`](https://developer.wordpress.org/block-editor/reference-guides/packages/packages-scripts/) to `simple-wp-helpdesk/assets/dist/`. **Dist files are committed** so end users installing from the GitHub release ZIP do not need Node.

## Rationale

`@wordpress/components` ships `Modal`, `Notice`, `Button`, `ComboboxControl`, `Popover` — directly covers our common UI primitives without a second component library. The `.asset.php` files auto-generated by wp-scripts auto-generate the `wp_enqueue_script` dependency array and the version hash, so PHP-side enqueue is one helper call. WordPress 6.0 (the v4.0 minimum) already loads `wp-element` (React) for the block editor, so declaring it as an external dependency adds ~0 KB to the plugin bundle.

## Source / build layout

```text
simple-wp-helpdesk/assets/
├── src/                      # ES modules (authored)
│   ├── toast/index.js        # global toast notification renderer
│   ├── admin-inbox/index.js  # admin ticket list (v4.0)
│   ├── views-settings/index.js  # admin settings tab interactions (v4.0)
│   ├── theme-violet/index.js # opt-in violet admin theme (v4.0)
│   ├── portal-v2/index.js    # messenger-style portal conversation (v4.0)
│   └── reports-v2/index.js   # reports dashboard (v4.0)
└── dist/                     # webpack output (committed)
    ├── <name>.js             # one per entrypoint
    ├── <name>.asset.php      # deps + version hash, included by PHP enqueue
    ├── style-<name>.css      # per-entrypoint CSS bundles (where applicable)
    └── style-<name>-rtl.css  # RTL variants (auto-generated)
```

## Entrypoints

Declared in `package.json` `build` script as `<name>=<path>` pairs passed to `wp-scripts build`:

| Entrypoint | Source | Purpose | Since |
|---|---|---|---|
| `toast` | `toast/index.js` | Global `swhToast()` renderer | v3.7.0 |
| `admin-inbox` | `admin-inbox/index.js` | Admin ticket list / inbox UI | v4.0.0 |
| `views-settings` | `views-settings/index.js` | Settings page tab interactions | v4.0.0 |
| `theme-violet` | `theme-violet/index.js` | Optional violet admin theme | v4.0.0 |
| `portal-v2` | `portal-v2/index.js` | Messenger-style portal conversation | v4.0.0 (#354) |
| `reports-v2` | `reports-v2/index.js` | Reports dashboard | v4.0.0 |

Adding a new entrypoint: extend the `<name>=<path>` list in both `build` and `start` scripts in `package.json`, add an `assets/src/<name>/index.js` file, and add a PHP enqueue call (see pattern below).

## Bundle-size budget

**≤ 40 KB gzip per entrypoint**, excluding WP-shipped externals (`wp-element`, `wp-components`, `wp-i18n`, `wp-data`).

Current measurements (v4.0.6 build, gzipped):

| Entrypoint | Size |
|---|---|
| `toast` | ~500 bytes (PoC, no externals) |
| `theme-violet` | small (CSS-only entrypoint, no JS imports) |
| `views-settings` | a few KB |
| `portal-v2` | low-double-digit KB |
| `reports-v2` | low-double-digit KB |
| `admin-inbox` | high-double-digit KB (dominant) |

To re-measure: `gzip -c simple-wp-helpdesk/assets/dist/<name>.js | wc -c`. Exact numbers should be captured in `performance-baseline.md` when that doc is refreshed.

The 40 KB cap exists because going much above that on the admin ticket list trips slow-first-paint on shared hosts. If a new feature needs more, split the entrypoint or lazy-load.

## PHP-side enqueue pattern

```php
$asset_file = SWH_PLUGIN_DIR . 'assets/dist/<name>.asset.php';
if ( file_exists( $asset_file ) ) {
    $asset = include $asset_file;
    wp_enqueue_script(
        'swh-<name>',
        SWH_PLUGIN_URL . 'assets/dist/<name>.js',
        $asset['dependencies'],
        $asset['version'],
        true
    );
}
```

The toast entrypoint has a dedicated helper (`swh_enqueue_toast_script()` in `includes/helpers.php`) because it's enqueued from many call sites. Other entrypoints are enqueued directly from the relevant admin/frontend class.

## i18n in JS

```js
import { __, sprintf } from '@wordpress/i18n';
```

Each script handle must have `wp_set_script_translations()` called on it after registration. Without that, the JS bundle ships English-only. See `i18n.md`.

## Migration path

Legacy unbuilt admin JS — `simple-wp-helpdesk/assets/swh-admin.js` and `swh-frontend.js` — remains in place for the surface that hasn't been migrated yet. As of v4.0.6 the following have moved to the build pipeline: toast notifications, admin inbox, settings tab interactions, violet theme, portal v2, reports v2. **Canned-response insertion, file-upload progress, and most form interactions are still in the legacy bundles.**

When migrating: the new module typically exposes a globally-callable function (`window.swhToast`, etc.) so existing legacy call sites resolve unchanged.

## CI integration

`make e2e-docker` depends on `make js-build`, which runs `npm install` (one-time) and `npm run build`. PHP-only gates (`make test-docker`) do not require Node — they validate the committed `assets/dist/` directly.

Release ZIPs are built by `release.yml` via `zip -r ... simple-wp-helpdesk/`, which includes `assets/dist/` automatically. No workflow changes were required.

---

## Dev workflow

```bash
npm install                 # one-time, or when package.json changes
npm run start               # watch mode during development
npm run build               # production build before commit
npm run lint:js             # ESLint via wp-scripts
npm run format              # Prettier via wp-scripts
```

**Always commit fresh `dist/` files when `src/` changes.** The pre-push hook does NOT rebuild for you — CI (`make e2e-docker`) does rebuild, so a stale dist will still be caught by tests, but you'll burn a CI cycle.
