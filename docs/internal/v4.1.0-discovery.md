## §2 — Rate-limit precedent

`grep -rn "swh_check_rate_limit"` returns **zero hits**. The plan's assumed helper name is wrong.

The actual helper is `swh_is_rate_limited()` at `simple-wp-helpdesk/includes/helpers.php:917`:

```php
function swh_is_rate_limited( $action, $ttl = 30 ) {
    // …
    $key = 'swh_rl_' . md5( $action . '_' . swh_get_client_ip() );
    // …
}
```

Signature: `swh_is_rate_limited( string $action, int $ttl = 30 ): bool`.
Storage: WP transient keyed `swh_rl_<md5(action_clientip)>`, TTL configurable via the `swh_rate_limit_ttl` filter.

**No `_clear_rate_limits()` test helper exists.** `grep -rn "_clear_rate_limits"` is empty. Tests in `tests/Unit/RateLimitTest.php` clear state by deleting transients directly.

**Per-action-per-ticket invariant** is enforced by `tests/Unit/Invariants/RateLimitKeyInvariantTest.php` — every portal call uses `portal_<close|reopen|reply>_<ticket_id>`.

**Implication for Phase 7:** the planned `RateLimiter` class cannot just "extend `_swh_check_rate_limit`" — that helper doesn't exist. Phase 7 must either:
- (a) **wrap** the existing `swh_is_rate_limited()` (simpler — preserves the no-custom-tables invariant and the existing transient layout), or
- (b) build a fresh class because the new API surface needs `{ allowed, remaining, reset }` and the existing helper only returns a bool.

Recommended path: **build the new class fresh** (option b) but model it after the existing helper's transient + client-IP + filter design. Add the `_clear_rate_limits()` test helper as new work in Phase 7 (§12 below).

→ Logged in §14.

## §4 — Reply insert sites

`grep -rn "comment_type.*helpdesk_reply\|'helpdesk_reply'" simple-wp-helpdesk/` returns 20+ hits. The **canonical admin "Add Reply" path** is in `admin/class-ticket-editor.php` (function `swh_save_ticket_data`, lines 565 and 595 — one for the internal note branch, one for the public reply branch):

```php
// simple-wp-helpdesk/admin/class-ticket-editor.php:595
$comment_id = wp_insert_comment(
    array(
        'comment_post_ID'      => $post_id,
        'comment_author'       => $current_user_name,
        'comment_author_email' => $current_user_email,
        'comment_content'      => $comment_content,
        'comment_approved'     => 1,
        'comment_type'         => 'helpdesk_reply',
    )
);
if ( $comment_id ) {
    update_comment_meta( $comment_id, '_is_user_reply', '0' );
    update_post_meta( $post_id, '_swh_last_activity_at', time() );
    swh_fire_ticket_replied( $post_id, $comment_id, get_current_user_id() );
    \SWH\Concurrency\TicketVersion::bump( $post_id );
}
```

The reply-insertion sequence the REST controller must reproduce:

1. `wp_insert_comment([...'comment_type' => 'helpdesk_reply'...])`.
2. For internal notes: `update_comment_meta( $cid, '_is_internal_note', '1' )` — see line 568.
3. For public replies: `update_comment_meta( $cid, '_is_user_reply', '0' )` (staff) or `'1'` (client).
4. `update_post_meta( $post_id, '_swh_last_activity_at', time() )`.
5. `swh_fire_ticket_replied( $post_id, $comment_id, get_current_user_id() )` — this is what dispatches the `swh_ticket_replied` action.
6. `\SWH\Concurrency\TicketVersion::bump( $post_id )`.

**No single function wraps this sequence today.** Phase 4 has two choices:

- (a) Duplicate the 6-step sequence in `RepliesController` and rely on PR review to keep it in sync. Fragile.
- (b) Extract a `swh_insert_helpdesk_reply()` helper as part of Phase 4, and call it from both `class-ticket-editor.php` and `RepliesController`. **Strongly preferred** — matches the plan's "writes route through existing handlers" rule.

→ Logged in §14 as a Phase 4 scope note (not a contradiction; the plan's "reuse the admin write path" intent is achievable but requires a small refactor first).

There is also a portal-side reply insert at `frontend/class-portal.php:582/700/784` which uses the same `comment_type` but a different (token-based) auth context. Phase 4 should NOT reuse the portal path.

## §5 — Ticket save helper

`swh_save_ticket_data` exists at `simple-wp-helpdesk/admin/class-ticket-editor.php:408`:

```php
add_action( 'save_post_helpdesk_ticket', 'swh_save_ticket_data', 10, 3 );
function swh_save_ticket_data( $post_id, $post, $update ) {
    if ( defined( 'DOING_AUTOSAVE' ) && DOING_AUTOSAVE ) { return; }
    if ( ! isset( $_POST['swh_ticket_nonce'] ) || ! wp_verify_nonce( ... ) ) { return; }
    if ( ! current_user_can( 'edit_post', $post_id ) ) { return; }
    // … 200+ lines: status/priority/assignee validation, reply insert, uploads, emails
}
```

**Critical:** this function is wired exclusively to the `save_post_helpdesk_ticket` action and short-circuits on:
1. Missing `$_POST['swh_ticket_nonce']` (a WP nonce, not a bearer token).
2. Missing `edit_post` capability on the current user.

It is **not callable from a REST context** without either fabricating `$_POST` superglobals (anti-pattern, would break sanitization) or refactoring.

→ Logged in §14. The plan's repeated claim that the REST controller "MUST call `swh_save_ticket_data()`" is unimplementable as-stated. Phase 3 must instead:

- Extract the sanitization / status-update / email-side-effect logic out of `swh_save_ticket_data()` into a context-neutral helper (e.g. `swh_update_ticket_fields( int $ticket_id, array $patch ): array<string,string>`), then call that helper from both `swh_save_ticket_data()` (admin path) AND the new `TicketsController` (REST path).
- Same applies to ticket creation — currently created by `wp_insert_post()` + meta on the admin side; a Phase 3 helper must be the new shared write path.

This is a real architectural decision that should land in Phase 3, not be hand-waved. The existing `src/Rest/TicketController.php` already PATCH-updates tickets via direct calls to `swh_set_ticket_status()` and `update_post_meta()` — Phase 3 should not copy that pattern (it bypasses `swh_save_ticket_data`'s sanitization).

## §8 — Settings storage (`integrations` group)

Read `simple-wp-helpdesk/src/Settings/Migration.php` (NOT `includes/Settings/Migration.php` as the plan says — see §14).

The `integrations` group currently contains **one** mapped option:

```php
// simple-wp-helpdesk/src/Settings/Migration.php:157-159
// Integrations group. Task 3.1: no direct get_option call sites;
// swh_inbound_secret exists in swh_get_defaults() — seeded here.
'swh_inbound_secret' => array( 'integrations', 'inbound_secret' ),
```

Storage shape: the migration produces a single option named `swh_settings_integrations` whose value is an associative array `[ 'inbound_secret' => '<string>' ]`. Read/write goes through `swh_get_option( 'integrations', 'inbound_secret' )` / `swh_set_option( 'integrations', 'inbound_secret', $val )`.

**Adding `swh_api_keys`:**

The new key does NOT need to go through the legacy-flat → grouped migration mapping (the `MAP` constant is for `v3.x → v4.0` migration only). For v4.1.0 net-new options, two patterns are available:

- Pattern A: store under the existing `integrations` group as `swh_get_option( 'integrations', 'api_keys', [] )`. Reads/writes the same `swh_settings_integrations` option bag.
- Pattern B: store as a top-level option `swh_api_keys` (the plan's current wording).

Pattern A matches the v4.0 grouped-options convention and is what `contract-settings.md` documents. **Recommend Pattern A.** Phase 1's data-dictionary entry should reflect that the key lives inside the `swh_settings_integrations` bag, not as a standalone option.

→ Logged in §14 as a "plan wording to tighten" item, not a contradiction.

## §14 — Plan contradictions found

**This section is non-empty.** Phase 1 cannot start until the user reviews and re-approves the plan with these corrections folded in. The plan-correction stub is appended to `plan_v4.1.0.md` as required by Phase 0 deliverable #3.

1. **File layout — `includes/REST/` → `src/Rest/`.**
   Plan repeatedly says new controllers / helpers go under `simple-wp-helpdesk/includes/REST/*`. The existing REST namespace lives at `simple-wp-helpdesk/src/Rest/` (PSR-4, `SWH\Rest\*`). New v4.1 controllers must follow the existing convention. Affects: Phase 1 (`ApiKeys.php`), Phase 2 (`Bootstrap.php`, `Auth.php`, `Errors.php`), Phase 3 (`TicketsController.php`, `Schemas/Ticket.php`), Phase 4 (`RepliesController.php`, `Schemas/Reply.php`), Phase 5 (`UsersController.php`, `CategoriesController.php`, `SettingsController.php`, `PublicSettingsAllowlist.php`), Phase 7 (`RateLimiter.php`), Phase 8 (`OpenApiController.php`). Same for `Admin/*` files referenced in Phase 6 and Phase 9 — they should land at `simple-wp-helpdesk/src/Admin/*` (matching the broader `src/` PSR-4 layout) OR `simple-wp-helpdesk/admin/*` (matching the existing legacy admin layout). The repo currently uses **both** — `admin/` for legacy procedural code, `src/` for namespaced classes. Phase 6 + 9 should declare which they prefer; recommend `src/Admin/*` for net-new namespaced PHP. (§1, §8)

2. **`Settings/Migration.php` path.**
   Plan: `simple-wp-helpdesk/includes/Settings/Migration.php`. Reality: `simple-wp-helpdesk/src/Settings/Migration.php`. (§8)

3. **Rate-limit helper name + signature mismatch.**
   Plan refers to `swh_check_rate_limit()` and `_swh_check_rate_limit()`. Neither exists. The real helper is `swh_is_rate_limited( string $action, int $ttl = 30 ): bool` at `includes/helpers.php:917`. Phase 7's `RateLimiter` class cannot "reuse" or "extend" the existing helper as-is — it returns a bool, not the `{ allowed, remaining, reset }` shape Phase 7 needs. (§2)

4. **`_clear_rate_limits()` test helper does not exist.**
   Plan tells Phase 7 to "extend the existing `_clear_rate_limits()` test helper". There is no such helper. Phase 7 must **create** it. (§12)

5. **`swh_save_ticket_data()` is not callable from REST.**
   The function short-circuits on missing `swh_ticket_nonce` POST field and on `current_user_can( 'edit_post' )` — neither is appropriate in a REST/bearer-token context. Phase 3's acceptance criterion ("`POST` / `PATCH` MUST call the same helpers that `swh_save_ticket_data()` calls") needs rewording: the controller cannot call `swh_save_ticket_data()` directly. Phase 3 must first **extract a context-neutral helper** (e.g. `swh_update_ticket_fields()`) that both the admin save-post path AND the REST controller can call. This is a real architectural refactor, not a thin adapter. (§5)

6. **No `swh_insert_helpdesk_reply()` wrapper for the canonical reply path.**
   Phase 4 says "reply insert MUST use the same write path that the admin 'Add Reply' form uses". The admin form's write path is a 6-step inline sequence in `swh_save_ticket_data()` — there is no single function to call. Phase 4 should first extract `swh_insert_helpdesk_reply( int $ticket_id, array $data ): int|false` and refactor `class-ticket-editor.php` to call it, then call the same helper from `RepliesController`. (§4)

7. **Playwright is pytest, not TypeScript.**
   Plan Phase 10 references `.spec.ts` files, `testing/e2e/sections/`, `playwright.config.ts`, `global-setup.ts`, TypeScript helper signatures. Reality: the E2E suite is **pytest** in `testing/scripts/test_helpdesk_pw.py`. Sections are numbered `test_NN_<slug>` functions. All Phase 10 file paths and helper signatures need rewriting in Python. (§10)

8. **Playwright section numbering resolved: start at 76, not 57.**
   Issue #370's "57–63" is stale. Highest shipped section is 75 (Integrations). v4.1 REST sections run 76–82. The plan's open-question #4 is now closed. Also note: issue #370 body says "Continuing numbering from section 56" — that wording should be corrected when the issue is closed in Phase 11. (§10)

9. **`swh_api_keys` storage location — wording.**
   Plan describes `swh_api_keys` as if it's a top-level option. v4.0 grouped-settings convention puts integration options under the `swh_settings_integrations` bag (read via `swh_get_option( 'integrations', 'api_keys' )`). Phase 1 + data-dictionary entry should clarify. (§8)

10. **`includes/REST/` path in Phase 0's own task list.**
    Phase 0 task #6 ("Read `simple-wp-helpdesk/includes/Settings/Migration.php`") refers to a path that does not exist. Cosmetic — corrected here. (§8)
