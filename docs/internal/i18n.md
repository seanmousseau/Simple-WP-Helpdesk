# Internationalization (i18n)

How user-facing strings flow from PHP/JS source into a translatable plugin.

> Internationalization is a hard invariant: **every user-facing string must be translatable**. This applies to admin UI, frontend portal, email templates, error messages, and JS-emitted strings. Hard-coded English text is a release blocker.

---

## Text domain

Single text domain across the entire plugin:

```text
simple-wp-helpdesk
```

Set in:

- The plugin header (`simple-wp-helpdesk/simple-wp-helpdesk.php`).
- Every `__()`, `esc_html__()`, `esc_attr__()`, `_n()`, `_x()` call as the second argument.
- The `.pot` file header in `simple-wp-helpdesk/languages/simple-wp-helpdesk.pot`.

Mismatched text domains silently fail to translate. PHPCS catches this — keep the gate green.

---

## PHP translation functions

| Use this | When |
|---|---|
| `__( 'String', 'simple-wp-helpdesk' )` | Returning a translatable string (no echo, no escape needed because it's not output yet) |
| `esc_html__( 'String', 'simple-wp-helpdesk' )` | Translatable string for HTML context — echoed safely |
| `esc_attr__( 'String', 'simple-wp-helpdesk' )` | Translatable string for an HTML attribute |
| `esc_html_e( 'String', 'simple-wp-helpdesk' )` | Translate + escape + echo in one call |
| `esc_attr_e( 'String', 'simple-wp-helpdesk' )` | Translate + escape + echo for attribute |
| `_n( 'one', 'many', $count, 'simple-wp-helpdesk' )` | Pluralization |
| `_x( 'Open', 'ticket status', 'simple-wp-helpdesk' )` | Same source string, different context (translator hint) |
| `_nx(…)` | Pluralization + context |

**Never** concatenate user input into a translatable string:

```php
// WRONG — breaks translators
echo __( 'Hello, ' . $name, 'simple-wp-helpdesk' );

// RIGHT
echo sprintf(
    /* translators: %s is the client's name */
    esc_html__( 'Hello, %s', 'simple-wp-helpdesk' ),
    esc_html( $name )
);
```

Always add a `/* translators: … */` comment on the line directly above a `printf`/`sprintf` with a placeholder.

## JS translation

JS strings use `@wordpress/i18n`:

```js
import { __, sprintf } from '@wordpress/i18n';

console.log( __( 'Saved', 'simple-wp-helpdesk' ) );
console.log(
    sprintf(
        /* translators: %s is the ticket UID */
        __( 'Ticket %s updated', 'simple-wp-helpdesk' ),
        ticketUid
    )
);
```

Enqueue the translations:

```php
wp_set_script_translations(
    'swh-admin-inbox',
    'simple-wp-helpdesk',
    SWH_PLUGIN_DIR . 'languages'
);
```

This must be called after the script is registered. Skipping it ships an English-only JS bundle.

## .pot generation

```bash
cd simple-wp-helpdesk
wp i18n make-pot . languages/simple-wp-helpdesk.pot --domain=simple-wp-helpdesk
```

Run before tagging a release. The `.pot` is committed.

JS strings: `@wordpress/scripts` does the extraction for the JSON catalogues per script handle. If you add a new JS entry point, regenerate.

## Translator notes

`/* translators: %s is the ticket UID */` style comments are extracted by `wp i18n make-pot` and presented to translators as context. Use them every time a string has:

- A placeholder (`%s`, `%d`, `%1$s`).
- A non-obvious term ("Drawer", "Inbox", "Helpdesk").
- Context that disambiguates from another use of the same string.

## What does NOT get translated

| Item | Why |
|---|---|
| The plugin name itself ("Simple WP Helpdesk") | Brand |
| Hook names (e.g. `swh_ticket_created`) | API identifiers |
| Status / priority **keys** | Stored as data, not displayed |
| Status / priority **labels as defined by operator** | The operator entered them in their own language; we render verbatim |
| CSS class names | — |
| Email template **placeholders** like `{name}`, `{ticket_id}` | Tokens, not language |
| Debug / log strings | Devs read those in English |

Note on statuses: the **default values** in `swh_get_defaults()` are English (`Open`, `In Progress`, etc.) and they ARE translatable when displayed by the plugin for users who haven't customised them. But once an operator overrides them via Settings → General, we render the operator's input verbatim — we don't try to translate operator-authored content.

## RTL (right-to-left)

The plugin's CSS uses logical properties where practical (`margin-inline-start` over `margin-left`, etc.) to play nicely with RTL locales. Verify on any new UI by toggling WordPress to `ar` (Arabic) or `he` (Hebrew) and checking layout.

WP's built-in RTL CSS pipeline (`rtl.css` siblings) is not currently used — the logical-property approach replaces it.

## Testing translations

For E2E or extended-test runs:

1. `wp site switch-language fr_FR` (or any installed locale).
2. Load translation file under `simple-wp-helpdesk/languages/simple-wp-helpdesk-fr_FR.mo` (or pull from translate.wordpress.org once we publish, currently we don't).
3. Verify the admin and frontend render translated strings.

For development without a real translation file, set `WPLANG=fr_FR` and check that strings are wrapped (PHPCS + manual eyeballing) — even without an `.mo` the wrapping is verifiable.

---

## PR-time checklist

When touching user-facing strings:

- [ ] Every new string uses `__()` / `esc_html__()` / `esc_attr__()` / etc.
- [ ] Every string uses the `simple-wp-helpdesk` text domain.
- [ ] Every `sprintf`/`printf` with a placeholder has a `/* translators: */` comment.
- [ ] No string concatenation across `__()` calls.
- [ ] For JS: `wp_set_script_translations()` is wired for the script handle.
- [ ] `.pot` regenerated if a release is imminent.
