## #356 — Settings schema migration (`swh_options` → topic sub-options)

**Current state:**

```
swh_get_option reads: 31
direct update_option('swh_*') writes: 10
Group key histogram:
  13 swh_get_option( 'tools'
  10 swh_get_option( 'general'
   6 swh_get_option( 'routing'
   2 swh_get_option( 'email'
```

**Note on missing groups:** `portal`, `notifications`, and `integrations` return zero hits in the histogram. Confirmed by scanning `simple-wp-helpdesk/{admin,includes,frontend}/` — no call sites for those three groups exist yet. This is consistent with v3.7.0 having wired only the call-site shape; the portal, notifications, and integrations settings still read from legacy flat options elsewhere or are not yet plumbed to `swh_get_option`. #356 must account for this when migrating the full 7-group schema.

**Migration shape:** v3.7.0 Phase 1 (#391) locked the 7-group call-site shape (`general`, `email`, `portal`, `notifications`, `tools`, `routing`, `integrations`). v4.0 #356 changes only the body of `swh_get_option()` and adds a corresponding `swh_set_option()` + a one-shot upgrade routine.

**Decisions still owed:**
1. Storage shape per group: 7 separate top-level options (`swh_settings_general`, etc.) vs. one `swh_settings` bag with 7 keys. Roadmap reads "topic sub-options" → 7 separate options.
2. Upgrade routine entrypoint: `register_activation_hook` vs. `plugins_loaded` + version-compare. Recommend `plugins_loaded` + `get_option('swh_db_version')` for idempotency on multisite + cron-driven activations.
3. Rollback story: forward-only migration vs. downgrade path. Recommend forward-only; v3.6 LTS branch is the supported sidegrade.
4. **Additional decision flagged by grep:** Three of the seven groups (`portal`, `notifications`, `integrations`) have zero `swh_get_option` call sites in `{admin,includes,frontend}/`. Before #356 migrates their backing storage, a call-site audit is needed to confirm where those settings are currently read (direct `get_option()` calls, constants, or not yet implemented). Without call sites, the upgrade routine could silently migrate keys that nothing reads.

**10 unique filter hooks found** (noting `swh_allowed_file_types` appears at two call sites, so 9 distinct hook names).

**Pre-3.0 deprecation candidates (cross-referenced against `docs/internal/api-contract.md`):**

No deprecation status table exists in `api-contract.md` as of 2026-05-21. The filter table (lines 72–82) lists all 9 hooks without a "Since" or "Deprecated" column. The action table *does* carry a "Since" column, where `swh_pre_ticket_create` and `swh_ticket_created` are marked `2.1.0` (pre-3.0), but they are action hooks outside #360's filter scope.

For the 9 filter hooks: none carry a version annotation in `api-contract.md`. Cross-referencing `docs/developer/deprecations.md`: the file confirms no hooks have been deprecated yet ("No existing hooks are deprecated in v3.7.0 — this file only lands the tools").

**#360 must therefore establish the "Since" column and deprecation status table as part of its scope.** Without that baseline, there is no authoritative record of which filters pre-date v3.0. Based on git history and the absence of a deprecation table, the following are the most likely pre-3.0 candidates (to be verified against git blame during #360 implementation):

- `swh_ticket_statuses` — fundamental status override; likely existed since early versions.
- `swh_ticket_priorities` — similarly fundamental.
- `swh_allowed_file_types` — upload extension override; likely pre-3.0.
- `swh_submission_data` — submit-form mutation hook; likely pre-3.0.
- `swh_autoclose_threshold` — cron threshold override; likely pre-3.0.

Filters `swh_sla_open_statuses`, `swh_rate_limit_ttl`, `swh_parse_template`, and `swh_email_headers` are more likely post-3.0 (SLA, rate-limiting, and template parsing features are newer), but git blame during #360 should confirm.

**Helpers (from Step 4):**

- `swh_do_deprecated_action()` defined in `includes/deprecations.php` ✅

**Mechanism:** Wrap each pre-3.0 filter call site in `swh_apply_deprecated_filter()`. Existing listeners still fire — they get `_doing_it_wrong` in debug mode. Removal target: v4.2 at the earliest (2-minor window per `docs/developer/deprecations.md`).

**Doc updates owed when #360 lands:** `docs/internal/api-contract.md` filter table — add "Since" column and mark each deprecated filter with the SWH version that deprecated it and the earliest-removal version.
