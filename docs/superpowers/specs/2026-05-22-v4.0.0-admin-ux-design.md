# v4.0.0 Admin UX Rewrite — Design Spec

**Date:** 2026-05-22
**Branch:** `release/v4.0.0`
**Issues:** #349 (inbox), #350 (drawer), #351 (⌘K palette), #352 (saved views), #353 (bulk bar)
**Scale target:** 3–10 technicians, 100–500 open tickets

## Goal

Replace the WordPress-default `WP_List_Table`-driven Tickets admin page with a Linear/Notion-style dense list + slide-over drawer pattern, plus a ⌘K command palette, persistent saved views, and a sticky bulk-action bar. Keyboard-first for power users, click-friendly for everyone else. Stays inside the WP admin chrome (no full takeover).

## Non-goals

- Live presence / WebSocket-driven real-time updates (out of scope; revisit if scale rises past 30 techs / 2000+ open).
- A full settings UI rewrite — settings keep their existing tabs page; only the Tickets list/edit experience changes.
- Mobile-first responsive design — usable on tablets+, but the primary target is desktop technicians. The list collapses gracefully on narrow viewports; the drawer becomes full-screen below ~900px.
- Replacing the standalone ticket edit page entirely — it stays for rare actions (tag management, attachments, customer history, merge).
- Per-ticket live cursors or "Alice is typing" indicators.
- Bulk delete and CSV export (deferred; bar covers status / assign / priority / tag / close only).

## Layout — overall shape

Page chrome lives inside WP admin's content area. The standard WP admin sidebar (left nav, "Posts / Pages / Helpdesk / …") stays untouched.

```
┌─────────────────────────────────────────────────────────────┐
│ [WP admin chrome — sidebar, page title bar]                │
│  ┌────────────────────────────────────────────────────────┐│
│  │ Tickets                            ⌘K Search & commands││
│  ├──────────┬─────────────────────────────────────────────┤│
│  │ SAVED    │ [filter chip row OR sticky bulk bar]        ││
│  │ VIEWS    ├─────────────────────────────────────────────┤│
│  │ ▸ Unas.. │ ☐ #1247  Login throwing 500s    bob@…  2h  ││
│  │   42     │ ☐ #1246  Cannot dl invoice      ali@…  3h  ││
│  │   My Op  │ ☐ #1245  Feature: dark mode     car@…  5h  ││
│  │   18     │ … virtual scroll past row N                ││
│  │   High   │                                             ││
│  │   7      │                                             ││
│  │ + Add    │                                             ││
│  └──────────┴─────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────────┘
```

### Top bar

- Page title `Tickets` on the left.
- `⌘K Search & commands` hint on the right (also a button — clicking opens the palette for non-keyboard users).
- No filter dropdowns at this level — filters live in the chip row inside each view.

### Left rail (saved views) — 160px

- Heading: `SAVED VIEWS` (uppercase, small).
- Each view is a row with name + badge showing match count. The active view has a 3px blue left border and bolded label.
- `+ Add view` action at the bottom of the rail.
- Default views shipped: **Unassigned**, **My Open**, **High priority**, **Resolved this week**. All four are global views (admin-managed) — technicians can hide them in their personal preferences but can't delete them.
- Personal views appear under a `MY VIEWS` subheading (renders only when the user has at least one personal view).

### List area

- **Filter chip row** at the top: shows the active filters for the selected view (e.g. `Status: Open ×`, `Priority: any ×`, `Sort: Last reply ↓`). Chips are mutable in place; clicking the × removes that filter (locally — to persist into the saved view, the user clicks "Save changes to view").
- **Rows ~36px tall.** Columns (in order): checkbox, ticket id, subject, customer email, last activity, age.
- Subject column truncates with ellipsis at row width.
- Background alternates (`#fff` / `#f6f7f7`) for legibility. Hover state lightens the row.
- Selected rows get a blue tint (`#e9f1fb`).
- Clicking anywhere except the checkbox opens the drawer for that ticket.
- Checkboxes toggle selection without opening the drawer.

### Density and virtual scroll

- **v4.0 ships with plain DOM rendering** (no virtual scroll). 500 rows × 36px = 18,000px tall list — fine on modern hardware.
- A `.swh-virtual-list` primitive is built and unit-tested but **opt-in via a setting** (`swh_settings_general.virtualize_inbox` boolean, default `false`). The setting flips visible once the perf-baseline data shows we need it; for v4.0 the goal is "shipped and working," not "tuned for 2000-row scale."

## Drawer (workhorse) — `.swh-drawer`

Slides over from the right at **55% viewport width** (min 600px, max 900px). Backdrop dims the list (`rgba(0,0,0,0.35)`) but doesn't fully cover it — operators can still see context.

### Open / close behavior

- **Open:** clicking a row anywhere except the checkbox.
- **Close:** Esc, click on backdrop, dedicated `×` button, or the `⤢ Open full page` button (which closes drawer and navigates to standalone ticket page).
- **Unsaved draft guard:** if the composer has content or any meta dropdown has been changed without save, closing prompts "Discard draft?" with a Cancel/Discard choice.

### Structure

1. **Header** (`#fafafa` background, 10px padding):
   - Line 1: `#1246 · Cannot download invoice PDF` (id + title, bold).
   - Line 2: `bob@example.com · opened 3h ago · last reply by Alice 12m ago` (small, muted).
   - Right side: `⤢` (open full page) + `×` (close) icons.

2. **Meta row** (`#fafafa`, 8px padding, below header):
   - Inline pill dropdowns: status, assignee, priority, tag (`+ tag` if none).
   - Status pill is color-coded by status (e.g. green for In Progress, gray for Open, blue for Resolved).
   - Changes to dropdowns save immediately (with optimistic UI + version check — see Concurrency below).

3. **Thread** (`#fff` background, scrollable, flex-1):
   - Customer messages: gray bubble (`#f6f7f7`).
   - Staff replies: blue-tinted bubble (`#e9f1fb`).
   - Internal notes: yellow bubble (`#fff8e5`) with `🔒 Internal note · author` label and yellow left border.
   - Each message header shows `author · timestamp` (and `staff reply` / `Internal note` tags as appropriate).

4. **Composer** (`#fafafa`, 10px padding, bottom of drawer):
   - Textarea with placeholder `Type your reply… (⌘+Enter to send)`.
   - Below textarea:
     - Checkboxes (left): `Internal note` (turns the message into an internal note instead of customer-visible reply), `Mark resolved on send`.
     - Action icons (left, continued): `📎 Attach`, `📋 Canned…` (opens a popover with ticket templates from `swh_settings_tools.ticket_templates`).
     - Buttons (right): `Save draft` (text button), `Send reply ⌘↵` (primary button).
   - Auto-save draft to `localStorage` keyed by ticket id every 5 seconds while typing.

### Concurrency

Each ticket gets a `_swh_version` post meta — integer, starts at 1 at creation, increments on every save.

- Drawer reads the version when it opens.
- All save requests (meta changes, replies) include the expected version in the payload.
- Server rejects writes if the stored version differs from the expected (HTTP 409 Conflict response).
- On 409, the drawer:
  1. Fetches the latest state.
  2. Shows a yellow notice at the top of the drawer: `Bob updated this 2 min ago — review changes`.
  3. Presents a "merge view" — what changed since the operator opened the drawer, color-coded.
  4. Operator's in-progress draft is preserved in the composer and not discarded.
  5. Save button changes to "Send anyway (rebased on Bob's changes)".

Internal notes and replies in the thread also include the version they were saved against — UI can detect "out-of-order" deliveries if a slow request lands after a faster newer one.

## ⌘K Palette — `.swh-command-bar`

Centered modal at top-third of viewport. Max width 600px. Dark backdrop (`rgba(0,0,0,0.5)`).

### Trigger

- Keyboard: `⌘K` (macOS) / `Ctrl+K` (Windows/Linux). Always active when the inbox is focused.
- Button: the `⌘K Search & commands` hint in the top bar.

### Input

- Single search box, autofocused on open.
- Empty input shows recent history (last 8 selections from this session).

### Result groups (rendered conditionally)

1. **Bulk commands** — only when ≥1 row is selected in the list. Renders first. Items: `Close`, `Close as Resolved`, `Close + Assign to…`, `Change status`, `Change priority`, `Assign to…`, `Add tag`. The top item (`Close`) is auto-selected; ↵ runs it.
2. **Tickets** — fuzzy match on `id`, `title`, `body`, `customer email`. Up to 5 results. Each shows `id · title · status · age`.
3. **Saved views** — fuzzy match on view name. Up to 4 results. Selecting switches the inbox to that view.
4. **Settings & pages** — fuzzy match on registered admin page titles + first-level settings field names. Up to 4 results. Selecting navigates.
5. **Technicians** (only when query starts with `@` or current selection has an assignee context) — fuzzy match on technician name/email. Selecting fills "Assign to [tech]" command.

### Footer

- Left: `↑↓` navigate · `↵` select · `esc` close.
- Right: selection count when relevant (`3 tickets selected`).

### Keyboard shortcuts visible inside palette

- Commands can carry a `⌘+letter` shortcut shown on the right of the row (e.g. `Close` shows `⌘D`). These shortcuts also work outside the palette when the inbox is focused and selection > 0.

## Saved Views — `.swh-tabs` (left rail rendering of view list)

### Captured params

A view is a JSON object stored as serialized PHP:

```php
[
    'name'      => 'High priority',
    'filters'   => [
        'status'   => ['open', 'in_progress'],
        'priority' => ['high', 'urgent'],
        'assignee' => null,             // null = any
        'category' => null,
        'search'   => '',
    ],
    'sort'      => 'last_reply_desc',   // enum
    'columns'   => ['id','subject','customer','activity','age'], // ordered subset
]
```

### Storage

- **Global views** (admin-managed, visible to all techs): `wp_options` key `swh_global_views` — array of view objects.
- **Personal views** (per-tech): `user_meta` key `swh_personal_views` — array.
- **Visibility prefs** (per-tech hidden global views): `user_meta` key `swh_hidden_global_views` — array of global-view ids.

### Management UI

- Inline in left rail: `+ Add view` opens a small popover with name input, then saves the current filter chip state as a personal view.
- Right-click (or `⋯` button on hover) on a view opens a menu: Rename, Edit filters, Make global (admin only), Hide (technician only), Delete (only for personal views).
- A dedicated `Settings → Helpdesk → Views` page lists all global views with full edit access (admin only).

### Default views shipped

| Name | Filters | Sort | Visible to |
|---|---|---|---|
| Unassigned | status: open + in_progress, assignee: none | last_reply_desc | all |
| My Open | status: open + in_progress, assignee: current_user | last_reply_desc | all |
| High priority | priority: high + urgent, status: open + in_progress | priority_desc | all |
| Resolved this week | status: resolved, resolved_at within 7d | resolved_at_desc | all |

## Sticky bulk-action bar — `.swh-bulk-bar`

Renders at the top of the list area (replacing the filter chip row) when **selection count > 0**.

### Layout

- Yellow-tinted background (`#fff8e5`) with a 2px yellow top border for visibility.
- Left: `N selected` label.
- Action buttons in order: **Status ▾** (dropdown), **Assign ▾** (dropdown), **Priority ▾** (dropdown), **Tag ▾** (dropdown), **Close** (primary button).
- Right: hint text `Esc to deselect · ⌘K for more`.

### Bounds

- Selection capped at **200 rows**. Selecting beyond 200 disables further checkboxes with a tooltip explaining the cap; the user must reduce selection or use a saved view first.
- All bulk actions hit a single REST endpoint (`POST /swh/v1/bulk-action`) with `{ action, params, ticket_ids: number[], version_map: {id: version} }`. Server applies optimistic-concurrency checks per ticket; partial failures return per-ticket success/conflict in the response body.

### Failure UX

- After execution, a toast shows `N succeeded, M conflicts (click to review)`. Clicking opens a small drawer showing the M conflicted tickets with their latest state.

## Tech stack

- **Build:** `@wordpress/scripts` 32.x (landed v3.7.0 #390). New entry points in `simple-wp-helpdesk/assets/src/admin-inbox/`, output to `simple-wp-helpdesk/assets/dist/`.
- **Externals:** `wp-element` (React), `wp-components`, `wp-i18n`, `wp-data`. All ship with WP 6.0 (v4.0 floor — landed v3.7.0 Phase 2 + v4.0 Phase 2 #358).
- **Components from `@wordpress/components`:** `Modal` (palette), `Notice` (concurrency banner), `Button`, `ComboboxControl` (assignee/tag dropdowns), `Popover` (canned-responses), `SearchControl` (palette input).
- **New SWH primitives:**
  - `.swh-drawer` (slide-over container + backdrop + Esc handler + draft guard).
  - `.swh-virtual-list` (optional virtual scrolling; off by default).
  - `.swh-command-bar` (palette modal + result groups + keyboard nav).
  - `.swh-tabs` (left-rail view list).
  - `.swh-bulk-bar` (sticky action bar with action dropdowns).
- **State management:** `@wordpress/data` stores. Store namespaces:
  - `swh/inbox` — current view, filter overrides, selection, list data.
  - `swh/drawer` — open ticket id, draft state, pending meta changes.
  - `swh/palette` — open state, query, recent history.
  - `swh/views` — global + personal view definitions, sync to/from REST.
- **REST endpoints (new, all under `/swh/v1/`):** `GET /tickets` (paginated list with filters/sort), `GET /tickets/{id}` (full drawer payload), `PATCH /tickets/{id}` (meta update with version check), `POST /tickets/{id}/reply` (with version check), `POST /bulk-action`, `GET/POST/DELETE /views`, `GET /palette/suggest` (recent + popular for empty query).
- **Settings reads:** all via `swh_get_option( $group, $key, $default )` (grouped storage, landed v4.0.0 Phase 3 #356).

## Implementation phases

Each phase produces a separate PR into `release/v4.0.0`. Tests are required for each phase.

### Phase A — Inbox shell + dense list + left rail (#349)

Replaces the current ticket list admin page. No drawer yet — clicking a row navigates to the existing standalone ticket page (same as today). Saved views render as static defaults; user CRUD comes in Phase D.

- New screen: `simple-wp-helpdesk/admin/class-ticket-inbox.php` mounted at the existing ticket list slug.
- React tree: `<Inbox>` ← `<TopBar>` + `<LeftRail>` + `<FilterChips>` + `<TicketList>` + `<EmptyState>`.
- REST: `GET /swh/v1/tickets?view=…&page=…&sort=…`.
- Falls back gracefully if JS is disabled — server-rendered list with the same columns.
- Tests: PHPUnit for REST endpoint shape + permission checks; Playwright section for "list renders, switching views changes results, filter chips work, pagination works."

### Phase B — Drawer + workhorse contents + concurrency (#350)

Adds the slide-over drawer. Clicking a row opens it instead of navigating away. Composer + meta-row + thread + concurrency wiring.

- New component: `<TicketDrawer>` (`assets/src/admin-inbox/drawer/`).
- New REST: `GET /swh/v1/tickets/{id}` (drawer payload), `PATCH /swh/v1/tickets/{id}` (meta), `POST /swh/v1/tickets/{id}/reply`.
- `_swh_version` post meta lifecycle: bump on every save in `swh_set_ticket_status()` (v3.7.0 invariant #1) + new equivalent for meta/reply paths.
- Draft persistence: `localStorage` keyed by ticket id + user id, expires 7 days.
- Tests: PHPUnit for version-check / 409 response; Playwright section for "open drawer, edit status, reply, concurrent-conflict recovery."

### Phase C — ⌘K palette + bulk-action bar (#351 + #353)

Both consume the same action primitives, so they ship together.

- New components: `<CommandPalette>`, `<BulkActionBar>`.
- New REST: `GET /swh/v1/palette/suggest`, `POST /swh/v1/bulk-action`.
- Selection capping at 200 rows enforced both client- and server-side.
- Bulk-action response shape: `{ succeeded: [ids], conflicts: [{id, version_now}] }`.
- Tests: PHPUnit for bulk endpoint with mixed-conflict response; Playwright section for "select 3 tickets, ⌘K Close, see toast, no conflicts" + "concurrent update on 1 of 3 → toast shows 2 succeeded, 1 conflict, conflict drawer opens."

### Phase D — Saved views (#352)

Adds personal/global views CRUD + management UI.

- New REST: `GET/POST/PATCH/DELETE /swh/v1/views` (with caps: technicians = personal CRUD; admins = personal + global CRUD).
- `+ Add view` popover in left rail.
- `⋯` menu on views: rename, edit filters, make global, hide, delete.
- Dedicated `Settings → Helpdesk → Views` admin page for global view management.
- Tests: PHPUnit for view CRUD + capability gates; Playwright section for "create personal view, save current filters, switch between views, admin promotes to global."

## Out of scope (separate plans)

- **Frontend + Reporting** (#354 Portal v2, #355 indigo refresh, #359 reports redesign) — different design surface.
- **REST API v1 public surface** (v4.1, #362–#370) — the `swh/v1/` endpoints introduced here are admin-only; v4.1 turns them into authenticated public APIs.
- **Webhooks** (v4.2) — consume the v3.7 lifecycle action hooks; no direct dependency on this design.
- **Mobile / responsive** — usable on tablets, degrades gracefully on phones (full-screen drawer, hidden left rail, list-only).

## Open questions (none load-bearing — defaults locked, can revisit)

1. Default sort for "Unassigned" view: locked as `last_reply_desc` here, but could argue for `created_desc` to prioritize new tickets that haven't been touched. Revisit after operator feedback in v4.0 beta.
2. Whether the `⤢ Open full page` button should be visible by default or hidden behind a `⋯` overflow menu. Locked as visible for now (discoverability > minimalism); easy to hide later.
3. Drawer width: locked at 55% viewport, min 600px, max 900px. Operators with ultra-wide monitors may want it narrower. Add a per-user preference if feedback warrants.
