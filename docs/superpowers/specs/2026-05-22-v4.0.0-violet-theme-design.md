# v4.0.0 Violet Theme (opt-in) — Design Spec

**Date:** 2026-05-22
**Branch:** `release/v4.0.0`
**Issue:** #355
**Closes:** the "Indigo design refresh + typography upgrade" parked decision (Option A — ship as opt-in)

## Goal

Add an operator-toggleable visual refresh to the SWH admin + client portal. Default-off: existing installs keep current visual identity. Operators opt in via Settings → General → Appearance. When enabled, both surfaces re-render with the Vivid Violet palette (violet-800 primary, Geist Sans typography, tighter letter-spacing, softer shadows). Email templates are out of scope.

## Non-goals

- **Email templates.** Emails ship in the existing visual identity. Inline-CSS + Outlook 2016 compatibility makes a second template stack too expensive for this release.
- **Custom palette builder.** The setting is binary — current theme OR violet theme. No per-token customization in v4.0.
- **Per-user preference.** The setting is site-wide (a `swh_settings_general` key), not per-user. A site-admin chooses for the whole instance.
- **Replacing dark mode.** The existing admin-color-scheme-driven dark mode (v3.6.0) continues to work; the violet theme has its own dark variant that activates on top of the same WP color scheme detection.
- **Migrating the default.** Even after v4.x, the violet theme stays opt-in. Flipping the default is a separate decision in a future major.

### Typography

- **Font stack (current):** `-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, sans-serif`
- **Font stack (violet):** `"Geist Sans", "Geist", -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, sans-serif`
- Geist Sans self-hosted via `simple-wp-helpdesk/assets/fonts/geist-{400,500,600,700}.woff2`. License: Open Font License (Geist is published by Vercel under OFL 1.1; we redistribute the WOFF2 files in the plugin per OFL clause 5).
- `font-display: swap` to avoid FOIT; `unicode-range: U+0000-007F, U+00A0-00FF` to ship only Latin glyphs (~28KB total across 4 weights).
- `letter-spacing: -0.005em` on body, `-0.01em` on headings (`<h1>`–`<h3>` and `.swh-drawer-title`).

### Spacing rhythm

- Spacing scale token map (CSS variables):
  - Current: 4 / 8 / 12 / 16 / 24 / 32 / 48 (the existing implicit scale).
  - Violet: 4 / 8 / 12 / 16 / 20 / 28 / 40 — tighter; replaces every magic-number padding/margin in the v4.0 admin-inbox SCSS files.
- Implemented as `--swh-space-1` through `--swh-space-7` so component CSS can use `padding: var(--swh-space-3) var(--swh-space-4)` instead of hardcoded pixels.

### Shadows

- Current shadows (e.g. `0 2px 8px rgba(0,0,0,0.1)` on cards) → violet shadows with tighter blur and a faint primary tint:
  - `--swh-shadow-sm`: `0 1px 2px rgba(46,16,101,0.06)` (current: `0 1px 1px rgba(0,0,0,0.04)`)
  - `--swh-shadow-md`: `0 2px 8px rgba(46,16,101,0.08), 0 1px 2px rgba(46,16,101,0.04)` (current: `0 2px 8px rgba(0,0,0,0.1)`)
  - `--swh-shadow-lg`: `0 8px 24px rgba(46,16,101,0.12), 0 2px 6px rgba(46,16,101,0.06)`
- Border radii: current uses mixed values (3px / 4px / 6px / 12px / 14px / 100px). Violet locks: 4px / 8px / 12px / 999px (pill).

### Border-radius rationalization

A small follow-on cleanup that ships with violet (and only when the theme is on) — the current admin-inbox CSS uses 3, 4, 6, 10, and 12px radii inconsistently. Violet activates a single rounded scale:

- `--swh-radius-sm`: 4px (inputs, small chips)
- `--swh-radius-md`: 8px (cards, drawer panels, buttons)
- `--swh-radius-lg`: 12px (modals, popovers)
- `--swh-radius-full`: 999px (pills, avatars)

When the theme is **off**, the existing hardcoded values stay.

## Architecture

### Setting

- Storage: `swh_settings_general.use_violet_theme` (bool, default `false`). Lives in the grouped storage shipped by Foundation #356.
- UI: Settings → General tab, new "Appearance" section. Single checkbox: "Use new Violet theme (preview)". Help text: "Updated visual identity for the admin + client portal. Restart your browser or hard-refresh after enabling to load the new fonts."
- Capability: `manage_options` (admins only — site-wide preference).

### CSS architecture

Two new files, both `@wordpress/scripts`-built:

```
simple-wp-helpdesk/assets/src/theme-violet/tokens.scss        # CSS-variable definitions (light + dark)
simple-wp-helpdesk/assets/src/theme-violet/components.scss    # Component overrides keyed by .swh-theme-violet selector
```

Build output:

```
simple-wp-helpdesk/assets/dist/theme-violet.css               # ~6KB gz (tokens + overrides)
simple-wp-helpdesk/assets/dist/theme-violet.asset.php
simple-wp-helpdesk/assets/fonts/geist-{400,500,600,700}.woff2 # checked in, not built
```

The theme stylesheet is only enqueued when the setting is on. PHP-side check in the existing admin + frontend enqueue paths:

```php
if ( swh_get_option( 'general', 'use_violet_theme', false ) ) {
    wp_enqueue_style( 'swh-theme-violet', SWH_PLUGIN_URL . 'assets/dist/theme-violet.css', array( 'swh-shared' ), SWH_VERSION );
    // Also add body class:
    add_filter( 'admin_body_class', static fn( $c ) => $c . ' swh-theme-violet' );
    // Frontend equivalent: filter body_class via a wrapper around the portal shortcodes.
}
```

The theme is **always scoped under `.swh-theme-violet`** so the same stylesheet can ship to operators with the theme off and have zero visual effect (defensive layering — should never fire, but keeps a single CSS bundle).

### Font loading

- Self-hosted Geist Sans 400/500/600/700 in `simple-wp-helpdesk/assets/fonts/`.
- `@font-face` rules emitted in `tokens.scss` with `font-display: swap` and `unicode-range: U+0000-007F, U+00A0-00FF`.
- Preload only when the theme is on:
  ```php
  add_action( 'wp_head', function () {
      if ( ! swh_get_option( 'general', 'use_violet_theme', false ) ) return;
      printf(
          '<link rel="preload" href="%s" as="font" type="font/woff2" crossorigin>',
          esc_url( SWH_PLUGIN_URL . 'assets/fonts/geist-400.woff2' )
      );
  } );
  ```

### Component coverage

Every v4.0 admin-inbox component + the existing portal shortcode markup gets a `.swh-theme-violet` selector override block. Concretely:

- `.swh-inbox` and all `.swh-inbox-*` descendants
- `.swh-drawer` + `.swh-message-*` + `.swh-drawer-composer`
- `.swh-palette-modal` + `.swh-palette-*`
- `.swh-bulk-bar`
- `.swh-helpdesk-wrapper` (portal root) + `.swh-portal-*` descendants
- Existing legacy components (badges, toast, panel groups, empty state) — also rebranded for visual consistency even though they predate v4.0.

### Dark-mode interaction

The existing dark-mode trigger (`body.swh-admin-theme-dark` from `swh_admin_color_is_dark()`) is preserved. When both classes are present (`.swh-theme-violet.swh-admin-theme-dark`), the violet-dark token set activates. Verified contrast ratios documented in the spec table above.

## Testing strategy

1. **PHPUnit** — single test that `swh_enqueue_violet_theme()` (or wherever the enqueue gate lives) calls `wp_enqueue_style` only when the setting is on; doesn't call it when off.
2. **Playwright** — single section `test_71_violet_theme_toggle`: load Settings, enable Violet, save, navigate to inbox, assert `body.swh-theme-violet` present, assert primary button background-color is `rgb(91, 33, 182)` (violet-800). Toggle off, reload, assert class gone.
3. **Visual regression — manual.** No screenshot diff harness in v4.0. Tester runs `make e2e-docker` with the toggle on AND off, eyeballs the result. Document the manual checklist in `testing-guide.md`.

The QA cost is real — every component must look right in 2 themes × 2 dark modes = 4 visual states. The Playwright `test_71` only confirms the toggle works; QA confirms the result is presentable.

## Implementation phases

Single PR into `release/v4.0.0`. No phase split — the work is cohesive enough for one PR (~12 files, mostly CSS + one PHP enqueue gate + one setting + one Playwright test).

1. **A.** Add `use_violet_theme` setting + UI checkbox in Settings → General → Appearance section. Wire into `swh_get_defaults()`.
2. **B.** Self-host Geist Sans WOFF2 files; add `@font-face` rules in `tokens.scss` with `font-display: swap` + `unicode-range`.
3. **C.** Write `tokens.scss` (CSS-variable definitions, light + dark) and `components.scss` (override blocks under `.swh-theme-violet`).
4. **D.** Add `theme-violet` entry to `package.json` `build` script; emit `theme-violet.css` + `.asset.php`.
5. **E.** Add conditional `wp_enqueue_style` + `admin_body_class`/`body_class` filters in the admin-inbox + portal enqueue paths.
6. **F.** Playwright section `test_71_violet_theme_toggle`.
7. **G.** Docs — update `design-guide.md` with the violet token table; update `data-dictionary.md` and `config-reference.md` for the new setting; CHANGELOG entry; check off #355 in roadmap; resolve the `parked_features.md` entry to "shipped as opt-in in v4.0".

## Open questions (none load-bearing — defaults locked)

1. **Logo treatment when violet is on.** Current logo (`swh_email_logo_url` option) is used in headers; on the violet theme it sits on cream/white backgrounds. If operators have a dark-themed logo, it'll look odd. Locked: ship as-is; document in design-guide.md as a known limitation operators can address by re-uploading a theme-appropriate logo.
2. **Geist license redistribution clause.** OFL 1.1 requires the license file to ship alongside the font binaries. Add `simple-wp-helpdesk/assets/fonts/LICENSE-OFL.txt` to the build.
3. **Backports.** The violet theme assumes the v4.0 component CSS (`.swh-inbox-*`, etc.). Earlier (v3.x) installs that upgrade-and-toggle won't have all selectors; they'll see partial styling. Mitigation: the violet theme is gated by v4.0+ implicitly (the inbox CSS lives in v4.0 dist), so toggling on a v3.7 install affects only the legacy portal + settings UI. Note in `release_v4.x.x_roadmap.md`: "Violet theme requires v4.0.0+; pre-4.0 surfaces won't be fully themed."
