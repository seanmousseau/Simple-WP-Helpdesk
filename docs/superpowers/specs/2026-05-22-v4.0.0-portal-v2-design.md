# v4.0.0 Portal v2 — Conversation-First Layout Design Spec

**Date:** 2026-05-22
**Branch:** `release/v4.0.0`
**Issue:** #354

## Goal

Replace the form-first client portal (current `swh_render_client_portal()` in `simple-wp-helpdesk/frontend/class-portal.php`) with a messenger-style conversation-first layout. The thread leads visually; the composer is pinned at the bottom; ticket-level actions (close, reopen, CSAT) live in a single `⋮` header dropdown.

The current portal places the reply form above the message history, which means customers see the form before context. They don't realize there IS a thread, or scroll past their own messages. Portal v2 inverts the hierarchy: conversation first, action affordances second.

## Non-goals

- **No new features.** v2 is a layout/markup refactor only. Same set of capabilities: view ticket, view thread, reply with attachments, close, reopen (when applicable), submit CSAT rating, ticket lookup form.
- **No React.** Portal stays server-rendered via PHP. Light vanilla JS (~3KB) for form-submit AJAX, auto-scroll, optimistic message append.
- **No new REST endpoints.** Reuses the existing portal POST handlers (`swh_handle_portal_reply`, `swh_handle_portal_close`, etc.). The new JS just hits them with `fetch` instead of full page reloads.
- **No typing indicator or live updates.** Static reads on page load; subsequent updates require an explicit refresh or sending a reply.
- **No attachment gallery.** Files remain inline in the message that uploaded them.
- **No layout shift for the lookup form.** It stays a separate page (`?action=lookup`), not embedded in the conversation view.

## Architecture

### Server rendering (PHP)

`swh_render_client_portal()` keeps its current responsibilities (token validation, ticket lookup, render dispatch). The interior markup it emits changes from a form-first stack to the messenger layout:

```
<div class="swh-portal-v2 swh-helpdesk-wrapper">
  <header class="swh-portal-v2-header">
    <div class="swh-portal-v2-header-titles">

      <div class="swh-portal-v2-status-pills">

        <span class="swh-pill swh-pill-priority">High</span>
      </div>

    <input type="hidden" name="token" value="<?php echo esc_attr( $token ); ?>" />
  </form>

```

The thread is rendered server-side using a new helper `swh_portal_render_thread( int $ticket_id ): string` in `simple-wp-helpdesk/frontend/class-portal.php`. The helper:
- Pulls comments with `get_comments( type='helpdesk_reply' )`.
- Skips internal notes (`_is_internal_note=1`) — those stay invisible to customers.
- Treats the post body as the synthetic first message.
- Returns HTML with appropriate `swh-msg-customer` / `swh-msg-staff` classes based on whether the comment author is a logged-in user.

### Markup decomposition

Three new template partials in `simple-wp-helpdesk/frontend/templates/portal-v2/`:

| File | Renders |
|---|---|
| `header.php` | Title, status/priority pills, `⋮` menu trigger + dropdown |
| `thread.php` | The full message list. Loops over comments, renders each via `_message.php`. |
| `_message.php` | A single bubble (customer or staff). Accepts `$author`, `$body`, `$gmt`, `$is_staff`. |
| `composer.php` | The pinned form. Handles textarea + attach + send + nonces + hidden ticket/token fields. |

The existing `swh_render_client_portal()` becomes a thin orchestrator that requires each partial in order.

### Light JS (~3KB)

New file `simple-wp-helpdesk/assets/src/portal-v2/index.js` (built via the existing `@wordpress/scripts` pipeline, parallel to `toast` and `admin-inbox` entries):

```js
// Pseudocode — concrete in the implementation plan.

// 1. Scroll thread to bottom on page load.
const thread = document.getElementById( 'swh-portal-thread' );
if ( thread ) thread.scrollTop = thread.scrollHeight;

// 2. Form submit → fetch POST → append new bubble optimistically.
const form = document.querySelector( '.swh-portal-v2-composer' );
if ( form ) {
    form.addEventListener( 'submit', async ( e ) => {
        e.preventDefault();
        const data = new FormData( form );
        const text = data.get( 'reply_body' ).trim();
        if ( ! text ) return;

        const optimisticBubble = createBubble( text, 'customer', 'just now' );
        thread.appendChild( optimisticBubble );
        thread.scrollTop = thread.scrollHeight;
        form.querySelector( 'textarea' ).value = '';

        const response = await fetch( window.swhPortalV2.replyUrl, { method: 'POST', body: data } );
        if ( ! response.ok ) {
            optimisticBubble.classList.add( 'swh-msg-failed' );
            // Restore textarea content so user can retry.
            form.querySelector( 'textarea' ).value = text;
        } else {
            optimisticBubble.classList.add( 'swh-msg-sent' );
        }
    } );
}

// 3. ⋮ menu open/close.
const trigger = document.querySelector( '.swh-portal-v2-menu-trigger' );
const menu = document.querySelector( '.swh-portal-v2-menu' );
if ( trigger && menu ) {
    trigger.addEventListener( 'click', () => {
        const open = ! menu.hidden;
        menu.hidden = open;
        trigger.setAttribute( 'aria-expanded', String( ! open ) );
    } );
    document.addEventListener( 'click', ( e ) => {
        if ( ! menu.contains( e.target ) && ! trigger.contains( e.target ) ) {
            menu.hidden = true;
            trigger.setAttribute( 'aria-expanded', 'false' );
        }
    } );
}

// 4. Cmd+Enter / Ctrl+Enter in textarea submits.
const textarea = form?.querySelector( 'textarea' );
textarea?.addEventListener( 'keydown', ( e ) => {
    if ( e.key === 'Enter' && ( e.metaKey || e.ctrlKey ) ) {
        e.preventDefault();
        form.requestSubmit();
    }
} );
```

The endpoint URL (`window.swhPortalV2.replyUrl`) is wired via `wp_localize_script` in the enqueue step. Existing portal POST handlers (`admin-post.php?action=swh_portal_reply` etc.) work unchanged — the new JS just calls them with `fetch` instead of full-page submit. On JS failure (network error, malformed response, JS disabled), the form falls back to the standard non-AJAX POST.

### Accessibility

- The `⋮` button has `aria-haspopup="true"`, `aria-expanded` toggles with the menu. Menu items are real `<button>` elements inside an `<ul>`.
- The thread `<main>` carries `role="log" aria-live="polite"` so screen readers announce optimistically-appended messages.
- Each `.swh-msg` is a real `<article>` with the author name + timestamp readable.
- Bubble colors maintain WCAG AA contrast against their backgrounds (verified: violet-800 on white = 8.6:1; default-theme primary on white = 4.9:1).
- The composer textarea has an implicit label via `placeholder`; add an `aria-label="Reply"` to be safe with screen readers (placeholders alone don't qualify as labels).
- Keyboard: Tab moves focus through header → thread (scrollable, focusable) → composer → send button. Cmd/Ctrl+Enter submits.
- Skip link from existing `.swh-skip-link` (v3.6 a11y work) lands on `#swh-portal-thread`.

### Backwards-compatibility shim

The existing portal URL shape (`?swh_ticket=N&token=ABC`) is unchanged. The token-validation flow in `swh_render_client_portal()` stays identical — only the render output changes. Existing bookmarks, emails containing portal links, and the inbound-email flow all continue to work.

No fallback shortcode or "use v1 portal" setting. v2 replaces v1.

## Testing strategy

1. **PHPUnit** — `PortalV2RenderTest`:
   - `test_render_thread_skips_internal_notes` — comments with `_is_internal_note=1` don't appear in the customer-facing thread.
   - `test_render_thread_marks_staff_replies` — comments with `user_id > 0` get `swh-msg-staff` class; anonymous get `swh-msg-customer`.
   - `test_render_thread_treats_post_body_as_first_message` — first synthetic bubble is the ticket's `post_content`.
   - `test_render_thread_orders_chronologically_asc` — oldest first.

2. **Playwright** — `test_72_portal_v2_renders_conversation`:
   - Submit a ticket as a guest. Capture portal URL from email-redirect or generated link.
   - Visit portal URL. Assert `.swh-portal-v2-header` exists. Assert `.swh-portal-v2-thread` contains at least one `.swh-msg-customer`.
   - Type a reply in the composer, click send (or Cmd+Enter). Assert a new `.swh-msg-customer` bubble appears optimistically.
   - Wait for response. Assert no `.swh-msg-failed` class.
   - Reload page. Assert the reply is still there (persisted server-side).
   - Click `⋮` → click "Close ticket". Confirm dialog. Reload. Assert pill says "Closed" and "Reopen ticket" item appears in menu.

3. **Manual visual check** — bubble alignment + colors look right in default theme AND violet theme; mobile breakpoint at 600px works.

## Out of scope (separate plans)

- **Real-time updates.** Polling the thread or SSE-pushing new staff replies. Out of scope; user reloads the page for fresh state.
- **Customer-facing typing indicator** ("Staff is replying…"). Out of scope; requires admin-side cursor signal + extra REST.
- **Attachment gallery.** Files stay inline in their owning messages.
- **Reply editing / deletion.** Customers cannot edit or delete their messages after sending. Status quo from v1.
- **Mobile app / PWA shell.** v2 is responsive but stays a regular web page.

## Open questions (none load-bearing — defaults locked)

1. **Avatars.** Should staff replies show the technician's WP avatar? Locked: NO in v4.0. Adds layout complexity (avatar column) and reveals the staff member's profile photo — a privacy choice operators haven't opted into. Reconsider in v4.1+.
2. **"Read receipts" for staff.** Could highlight when the customer last viewed the ticket (last token-validated GET timestamp). Locked: NO — no current tracking; would need a new meta key + write.
3. **Read-only mode after close.** Composer disabled on closed tickets, with "Reopen to reply" prompt? Locked: NO — keep composer enabled but Send button shows a tiny "this will reopen the ticket" hint when ticket is closed. Pre-empts the most common confusion.
