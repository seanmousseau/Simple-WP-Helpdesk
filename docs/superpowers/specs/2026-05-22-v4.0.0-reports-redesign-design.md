# v4.0.0 Reports Redesign — Drill-down + Period-over-Period Design Spec

**Date:** 2026-05-22
**Branch:** `release/v4.0.0`
**Issue:** #359

## Goal

Add two capabilities to the existing reports (`class-reporting.php` + `class-reporting-ui.php`) without rewriting them:

1. **Drill-down** — clicking a chart segment or KPI tile navigates to the inbox with a filter URL-hash applied (e.g. clicking "Open: 47" on the status breakdown chart → `edit.php?post_type=helpdesk_ticket#view=status:open`).

2. **Period-over-period comparison** — every report respects a time-range selector (7d / 30d / 90d / YTD / Custom) and displays a delta vs. the same-length prior period (`↑12% vs prior 30d`).

The chart visuals, the rendering library, and the AJAX endpoint shape stay the same. We're extending — not rebuilding.

## Non-goals

- **No new analytics dashboard.** This is enhancement only; the dashboard option was explicitly out of scope (deferred to v4.1 if ever).
- **No new chart library.** Keep whatever the existing UI uses (likely Chart.js or vanilla SVG — verify during implementation).
- **No KPI re-architecture.** Existing reports (`status_breakdown`, `avg_resolution_time`, `weekly_trend`, `first_response_time`, `kpi`) stay; they each gain the period selector + comparison metadata.
- **No drill-down for non-categorical reports.** `avg_resolution_time` and `first_response_time` are single numbers — they get period-over-period only, no drill-down.
- **No saved date-range presets** beyond the 4 standard + custom. Operators wanting "last fiscal quarter" set a custom range manually.
- **No CSV export from reports.** Deferred. Operators export via WP-CLI or the existing admin list bulk export.

## Architecture

### Time-range selector

A new toggle bar at the top of the reports page (one component, reused across all charts):

```
[ 7d | 30d | 90d | YTD | Custom ]    Period: 2026-04-22 → 2026-05-22 ↔ Prior: 2026-03-23 → 2026-04-22
```

- Default selection: `30d`.
- Stores selection in `localStorage` under `swh_reports_range` (per-user, per-browser preference). Restores on next visit.
- Custom range shows two `<input type="date">` fields inline. No third-party date-picker dependency.
- The visible "Prior" range is calculated as the same length immediately preceding the selected range. For YTD, prior is "same period last year" (Jan 1 → today, last year).
- Selecting a range fires a single event; every chart re-fetches with the new range params.

### Report payload shape (extension)

Existing AJAX endpoints (`wp_ajax_swh_report_data` with `?type=status_breakdown` etc.) gain optional query params:

- `range_start` (ISO date, e.g. `2026-04-22`)
- `range_end` (ISO date)
- `compare_to_prior` (bool, default `true`)

The response shape extends — never breaks existing callers:

```json
{
    "data": { /* same shape as today */ },
    "prior": { /* same shape, computed for the prior period; null if compare_to_prior=false or no comparable prior */ },
    "range": { "start": "2026-04-22", "end": "2026-05-22" },
    "prior_range": { "start": "2026-03-23", "end": "2026-04-22" }
}
```

Existing UI that doesn't read `prior` continues to work. The new range-aware UI reads both `data` and `prior` to compute deltas.

### Comparison delta UI

Each report card or chart shows a small comparison chip:

- `↑ 12.5% vs prior 30d` (green if "good", neutral if directional ambiguous)
- `↓ 8.2% vs prior 30d` (red if "bad")

The semantic direction (good/bad) is encoded per report:

| Report | Higher is | Lower is |
|---|---|---|
| `status_breakdown` (Open) | bad | good |
| `status_breakdown` (Closed/Resolved) | good | bad |
| `avg_resolution_time` | bad | good |
| `first_response_time` | bad | good |
| `weekly_trend` (new tickets) | ambiguous (depends on perspective) | ambiguous |
| `kpi` (varies per field) | mixed | mixed |

For ambiguous reports, the delta shows in neutral gray with no good/bad coloring.

### Drill-down

Categorical reports (`status_breakdown`, `weekly_trend` weeks) become clickable. Click handlers navigate to:

```
edit.php?post_type=helpdesk_ticket#filter=<facet>:<value>&range_start=<iso>&range_end=<iso>
```

Examples:
- Status breakdown's "Open" segment → `#filter=status:open&range_start=2026-04-22&range_end=2026-05-22`
- Weekly trend's "Week of 2026-04-22" bar → `#filter=created_between:2026-04-22..2026-04-28`

The inbox (`admin-inbox/index.js`) reads `window.location.hash` on mount, parses the `filter=` token, and dispatches a synthetic view to the `swh/inbox` store. The store accepts these synthetic views in addition to the default + saved ones.

Synthetic-view shape:

```js
{
    key: 'drilldown',
    label: 'Open tickets · last 30d',   // computed from filter values
    filters: { status: ['open'], created_between: ['2026-04-22', '2026-05-22'] },
    sort: 'last_reply_desc',
    isSynthetic: true,
}
```

When `isSynthetic`, the inbox left rail shows the synthetic view at the top with a small "× Clear" button. Clearing returns to whatever was active before the drill-down.

### REST endpoint update

`InboxController::build_query_args` extends its switch to support hash-driven filter inputs. Two new view keys: `status:<name>` and `created_between:<start>..<end>`. These aren't UI-selectable from saved views; they're only navigated to via drill-down URL hash.

```php
case 'status:open':
case 'status:in_progress':
case 'status:resolved':
case 'status:closed': {
    $status = substr( $view, strlen( 'status:' ) );
    $base['meta_query'] = array(
        array( 'key' => '_ticket_status', 'value' => $status, 'compare' => '=' ),
    );
    break;
}
case 'created_between':
    // Date-range filter via post_date.
    $range = (array) $request->get_param( 'created_between' );
    $base['date_query'] = array(
        array( 'after' => $range[0], 'before' => $range[1], 'inclusive' => true ),
    );
    break;
```

## Data model additions

None. The reports work off existing post meta + comments. Range params are URL-scoped, not stored.

The `swh_reports_range` localStorage key is JS-side only (no PHP, no migration).

## Implementation phases

Single PR into `release/v4.0.0`. ~8 tasks; suggested ordering:

1. **A.** `swh_report_status_breakdown()` etc. accept `$range_start` / `$range_end` / `$compare` args. PHPUnit covers prior-period math: e.g. "selected = 2026-04-22 → 2026-05-22; prior = 2026-03-23 → 2026-04-22".
2. **B.** AJAX dispatcher in `swh_ajax_report_data` reads the new params from `$_POST`/`$_GET`, forwards to the report functions. Response shape extended with `prior` + `range` + `prior_range`.
3. **C.** `class-reporting-ui.php` renders the range-selector toggle bar at the top + delta chip slots beside each chart. Default markup is server-side; range selector is JS-enhanced.
4. **D.** New `assets/src/reports-v2/index.js` — small vanilla JS that wires the range selector, persists to localStorage, re-fetches on change, paints delta chips.
5. **E.** Drill-down click handlers on chart segments (depending on existing chart lib's event API). Each segment carries a `data-filter-key` + `data-filter-value` attribute; the click navigates to the inbox URL with the right hash.
6. **F.** `InboxController::build_query_args` extends with `status:*` + `created_between` view keys.
7. **G.** `admin-inbox/index.js` reads `window.location.hash` on mount; if `filter=` present, parses and dispatches a synthetic view. `LeftRail` renders the synthetic view with a "× Clear" button.
8. **H.** Playwright `test_73_reports_range_and_drilldown`: load reports, switch to 90d, verify delta chip updates, click a status segment, verify inbox loads with filter active.
9. **I.** Docs: CHANGELOG, roadmap check-off, api-contract update for the new AJAX params.

## Open questions (none load-bearing — defaults locked)

1. **Comparison for YTD when no prior-year data exists.** First-year operators have no comparable prior period. Locked: if prior-range query returns zero or no data points, the delta chip shows "— no prior data" in muted gray.
2. **Custom range upper bound.** Allow ranges longer than the data history? Locked: no upper bound enforced. If the operator picks 2020-01-01 → today and the plugin was installed in 2024, the chart just shows what's there.
3. **Drill-down preserves the active inbox view.** When the operator clears the synthetic drilldown view, they return to whatever was previously active. The "before" view is held in JS-side state (not persisted) and naturally restored.
4. **Mobile.** Reports page on mobile collapses the range toggle to a `<select>` dropdown and stacks chart cards vertically. No separate mobile design.

## Out of scope (future)

- **Real-time / live-updating charts.** Static fetches only.
- **Export (CSV, PDF).** Operators can screenshot or use WP-CLI.
- **Custom report builder.** Locked report set.
- **Dashboard widgets in WP-admin home.** Out of scope.
- **Per-technician reports.** Reports are global; per-tech leaderboards belong in a future enhancement.
